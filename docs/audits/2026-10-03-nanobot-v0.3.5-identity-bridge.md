# NEXORA — Nanobot v0.3.5 Compatibility Audit

Date: 2026-10-03
Scope: LIA agent runtime integration only.
Excluded: PC-local integration and Stream Deck.

## Executive result

Nanobot v0.3.5 is technically compatible with NEXORA as an external agent runtime, but the integration must use an HTTP process boundary rather than embedding the Python SDK inside the Next.js/Vercel runtime.

Recommended first integration surface:

`NEXORA/Vercel → authenticated Nanobot gateway/API → Nanobot runtime → governed NEXORA capabilities`

## Identity bridge

NEXORA is the authority for authenticated user identity, goal/run correlation, autonomy ceiling and authorization. Nanobot receives a server-issued short-lived execution context and must never choose the effective NEXORA user identity.

The context is:
- HMAC-signed;
- short-lived (10–120 seconds);
- bound to user, LIA agent identity, organization, goal/run, session and autonomy ceiling;
- stored hashed server-side with a nonce and revocation state;
- rejected when expired, revoked, malformed, signature-invalid or mismatched with its persisted record.

MCP accepts this bridge token in addition to the existing Supabase-user bearer flow. For bridge-authenticated calls, NEXORA creates a server-side Supabase client and still executes every tool through the normal Policy Engine and Decision Gate.

The effective autonomy for delegated execution is:

`min(context.autonomyLevel, currentNexoraAutonomy)`

Therefore an old or delegated context cannot increase the user's current autonomy ceiling.

## MCP identity chain

`NEXORA authenticated user → signed execution context → Nanobot → /api/mcp → Policy Engine → NEXORA tool`

No `userId` is accepted from model/tool arguments.

## Deployment boundary

The Nanobot runtime remains external and persistent. Vercel hosts the stateless NEXORA boundary and does not host the long-lived Nanobot workspace.

## Acceptance criteria

1. NEXORA can mint a short-lived Nanobot context server-side.
2. MCP can validate the context without trusting model-supplied identity.
3. Expired/revoked/malformed contexts are rejected.
4. Context identity must match the persisted server record.
5. Delegated autonomy cannot exceed the current NEXORA autonomy.
6. Every MCP tool call still passes the existing NEXORA executor and Policy Engine.
7. Existing Supabase-user MCP authentication remains supported.
8. Bridge context tokens are not stored in plaintext.
9. Multi-user isolation is preserved by the user-bound execution context and explicit user scoping in the executor.
