# NEXORA — Nanobot v0.3.5 Compatibility Audit

Date: 2026-10-03
Scope: LIA agent runtime integration only.
Excluded: PC-local integration and Stream Deck.

## Executive result

Nanobot v0.3.5 is technically compatible with NEXORA as an external agent runtime, but the integration must use an HTTP process boundary rather than embedding the Python SDK inside the Next.js/Vercel runtime.

Recommended first integration surface:

NEXORA/Vercel
→ authenticated Nanobot gateway/API
→ Nanobot agent runtime
→ Nanobot native memory/Dream + MCP + subagents + long-running execution
→ governed NEXORA capabilities

The Python SDK is not the first integration surface because NEXORA is a Next.js/TypeScript application deployed on Vercel, while Nanobot's SDK is Python. Nanobot explicitly provides an OpenAI-compatible HTTP API for separate processes.

## 1. SDK compatibility

### Finding

Nanobot exposes two relevant integration surfaces:

- Python SDK: direct access to runtime, sessions, memory, hooks and stream events.
- OpenAI-compatible API: HTTP `/v1/chat/completions`, with `session_id` support.

For NEXORA, the OpenAI-compatible API is the correct initial boundary because it preserves process isolation between the TypeScript/Vercel application and the Python Nanobot runtime.

### Decision

Use:

`NEXORA Next.js → HTTPS → Nanobot API`

Do not add Python execution to the NEXORA Vercel application.

## 2. Memory

### Finding

Nanobot already provides:

- session messages;
- compressed `memory/history.jsonl`;
- `SOUL.md`;
- `USER.md`;
- `memory/MEMORY.md`;
- Dream consolidation;
- Git-backed memory changes.

### Decision

Nanobot remains the single general-purpose agent-memory runtime for LIA.

NEXORA must not create a competing general-purpose memory implementation.

NEXORA may continue to persist:
- governance/audit records;
- financial/domain data;
- product state;
- evaluation and telemetry;
- goals and execution state.

### Critical multi-tenant requirement

Nanobot documentation states that separate users/products/contexts should use separate config/workspace paths when isolation is required.

Therefore a shared Nanobot workspace must NOT be used for multiple NEXORA users.

Required design:

`user/tenant identity → isolated Nanobot workspace/config`

This is a deployment architecture requirement, not an optional optimization.

## 3. MCP

### Existing NEXORA capability

NEXORA already exposes `/api/mcp` with bearer authentication, an `mcp` scope, Supabase identity validation and policy-gated tool execution.

This is a strong foundation for Nanobot integration.

### Blocking issue

The current NEXORA MCP endpoint derives the user identity from the authenticated bearer token.

Nanobot's remote MCP configuration uses configured headers. A single static service token would therefore not safely represent multiple NEXORA users.

We must not solve this by passing a `userId` argument to financial tools or trusting model-supplied identity.

### Required solution

Introduce a dedicated authenticated service boundary for Nanobot that carries a server-issued, short-lived user execution context.

The identity chain must remain:

`NEXORA authenticated user → signed/short-lived execution context → Nanobot → governed NEXORA tool gateway`

The Nanobot model must never choose the effective NEXORA user identity.

## 4. Subagents

Nanobot supports bounded subagent concurrency.

### Decision

NEXORA remains the owner of:
- goal;
- authorization;
- autonomy ceiling;
- risk class;
- human approval;
- evaluation;
- final completion authority.

Nanobot may own:
- delegated execution;
- parallel helper work;
- intermediate tool calls.

A Nanobot subagent must therefore inherit the parent execution context and cannot escalate autonomy.

Required invariant:

`child autonomy ≤ parent autonomy`

## 5. Long-running tasks

Nanobot's gateway is designed for long-running work, heartbeat, Dream, cron and persistent sessions.

### Decision

Long-running work should be represented by a NEXORA goal/run identifier and delegated to Nanobot.

NEXORA retains durable execution state and recovery authority.

Nanobot is the execution worker, not the source of truth for financial goal completion.

Required correlation:

`NEXORA goal/run ID ↔ Nanobot session/task ID`

## 6. Automations

Nanobot provides scheduled automations, local triggers and heartbeat.

NEXORA already has Loops and runtime scheduling.

### Decision

Do not replace NEXORA Loops.

Use Nanobot automation primitives only as an execution mechanism behind a NEXORA-owned loop/goal.

External triggers must enter through an authenticated NEXORA boundary and must not directly mutate financial state.

## 7. Model routing

Nanobot supports model presets and fallbacks.

NEXORA already has a model/response runtime and telemetry.

### Decision

Nanobot may perform provider/model fallback inside its delegated runtime, but NEXORA retains the task-level routing policy.

Required observability:
- requested model/preset;
- selected model;
- fallback reason;
- latency;
- token usage when available;
- failure/retry;
- correlation ID.

## 8. Observability

Nanobot supports Langfuse tracing for supported OpenAI-compatible provider calls and the SDK exposes structured stream/runtime events.

NEXORA already records production telemetry and agent runs.

### Decision

Keep NEXORA as the product-level audit source and correlate Nanobot traces with:
- user ID;
- NEXORA goal/run ID;
- Nanobot session ID;
- task ID;
- tool call ID;
- model/provider;
- result status.

Do not treat Langfuse as an authorization or financial audit authority.

## 9. Vercel deployment

Vercel Functions can run Node.js/Python functions for extended durations on eligible plans, but that does not make Vercel a persistent Nanobot gateway host.

Nanobot's own deployment model expects a long-running gateway for WebUI, Dream, heartbeat, cron, sessions and channel connections.

### Decision

Use:

`Vercel NEXORA → HTTPS → external persistent Nanobot runtime`

The external runtime may be containerized/server-hosted with persistent storage.

The NEXORA Vercel application must remain stateless with respect to Nanobot's workspace.

## 10. Integration phases

### Phase A — compatibility adapter

- Add a server-only NEXORA Nanobot client.
- Require an authenticated Nanobot endpoint and secret.
- Add request timeout and response-size limits.
- Add correlation IDs.
- Fail closed if Nanobot is unavailable.
- Keep current deterministic LIA fallback.

### Phase B — identity bridge

- Define short-lived execution context.
- Bind it to NEXORA user + goal/run + autonomy ceiling.
- Reject expired, replayed or mismatched contexts.
- Never accept user identity from model/tool arguments.

### Phase C — MCP bridge

- Let Nanobot consume only the explicitly allowed NEXORA MCP/tool surface.
- Enforce NEXORA Policy Engine before every governed tool execution.
- Add regression tests for cross-user isolation.

### Phase D — Nanobot capabilities

- Enable native memory/Dream.
- Enable bounded subagents.
- Enable long-running execution.
- Integrate automation primitives with NEXORA Loops.
- Integrate model fallback.
- Integrate tracing.

### Phase E — production deployment

- persistent workspace storage;
- isolated workspace/config per user or tenant;
- secret management;
- health checks;
- restart/recovery;
- rate limits;
- concurrency limits;
- network allowlist;
- audit correlation.

## 11. Acceptance criteria

The integration is not considered production-ready until all are true:

1. A NEXORA user can start a Nanobot-backed LIA session.
2. The same session resumes after the HTTP request ends.
3. Nanobot memory survives runtime restart.
4. Different NEXORA users cannot read each other's memory.
5. Nanobot cannot bypass NEXORA Policy Engine.
6. A child subagent cannot increase autonomy.
7. A Nanobot task is correlated to a NEXORA goal/run.
8. A Nanobot outage produces a controlled LIA fallback/error.
9. MCP tool execution is user-bound and server-authorized.
10. Long-running work can recover after worker restart.
11. Model fallback remains observable.
12. Sensitive prompts/results are not unintentionally copied to third-party observability systems.
